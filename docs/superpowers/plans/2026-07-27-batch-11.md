## Task 1 — WinHTTP in `platform`

The tree has **no HTTP at all**. This task adds the smallest thing that works and nothing more, so
that task 2 is about the update check rather than about sockets.

`src/platform/http.odin`, hand-declaring WinHTTP the way `dwrite.odin` hand-declares DirectWrite:

```odin
Http_Result :: enum u8 { Ok, Network, Timeout, Too_Large, Bad_Status }
// Blocking GET. Caller owns `body`. NEVER call from the UI thread — see task 2.
http_get :: proc(host, path: string, max_bytes: int, timeout_ms: int, allocator := context.allocator)
    -> (body: []u8, status: int, res: Http_Result)
```

- HTTPS only. `WinHttpOpen` → `Connect` → `OpenRequest(WINHTTP_FLAG_SECURE)` → `SendRequest` →
  `ReceiveResponse` → read loop → close every handle on every path, including errors. A leaked
  session handle is a leaked thread pool.
- **Both timeouts set** (`WinHttpSetTimeouts`: resolve, connect, send, receive). The failure this
  prevents is a captive portal or dead DNS hanging the caller forever.
- **`max_bytes` enforced during the read loop, not after** — refuse and return `.Too_Large` rather
  than allocating whatever the server sends.
- A `User-Agent` header (GitHub rejects requests without one).
- No cookies, no auth, no redirects to a different host.

**Tests — `httptest`:** this is the one place a network dependency is unavoidable, so make the test
*not* require one. Test the pure parts directly (URL splitting, the size cap against a synthetic
reader if you factor one out) and make the live call **opt-in** behind an argument, printing SKIPPED
otherwise. A suite that fails on an offline machine is a suite people learn to ignore. If you cannot
factor a seam that lets the cap be tested without a socket, say so rather than shipping an untested
cap.

**Commit:** `Add a bounded HTTPS GET to the platform layer`

## Task 2 — Check for Updates

A `Help ▸ Check for Updates` menu row and a palette command.

**Never on the UI thread.** CLAUDE.md: the main thread builds UI and handles input and nothing else.
Use the established job pattern — copy inputs, work in private memory, publish once, poll a cancel
flag — the same shape as the line-count indexer (`doc.odin`'s `Line_Index`) and the search worker
(§6e). **Read one of them and mirror it; do not invent a third shape.** Teardown must cancel and
join: a worker that outlives the window is worse than no updater.

One request in flight — a second invocation while one is running does nothing (or says "checking…").

**The version compare is pure, and it is where the bug will be.** `v0.19.0` vs `v0.9.0` is not a
string compare; string order says 0.9.0 is newer. Parse three integers.

```odin
// "v0.19.0" / "0.19.0" -> (0,19,0). ok=false on anything else.
version_parse :: proc(s: string) -> (major, minor, patch: int, ok: bool)
version_newer :: proc(a, b: [3]int) -> bool
```

Test it hard: `0.19.0 > 0.9.0`, `0.10.0 > 0.9.9`, equal is not newer, a leading `v` optional, a
missing component, a non-numeric component, an empty string, a huge number. **A tag that does not
parse is "could not check", never "up to date"** — the safe answer when you do not know is not
silence.

**Parse the response defensively.** It is untrusted bytes from the network. Scan for `"tag_name"` and
take the following string; do not add a JSON dependency for one field. Truncated, malformed,
unexpected — all "could not check".

**Result surfacing:** up to date; a newer version with an offer to open the releases page via the
existing `shell_open_url`; or "could not check" with the reason in the log. Say **in the menu row
itself** that it contacts GitHub — the user should not have to guess which command touches the
network.

**Privacy:** no identifiers, no query parameters, no telemetry, nothing but a plain GET.

**Tests — extend `updatetest`:** the version compare exhaustively; the `tag_name` extraction against
good, truncated, and hostile fixtures; "could not check" on every failure path. Sabotage the compare
with a string comparison and watch `0.19.0` vs `0.9.0` go red — that is the one assertion that
matters most.

**Commits:** `Compare versions numerically` · `Add Check for Updates`

## Task 4 — the installer, and the signing-ready pipeline

**`installer/newtpad.iss`:**

- Per-user install to `%LOCALAPPDATA%\Newtpad`, **no elevation** — which is also what keeps the
  `HKCU` registration working exactly as `install.ps1` does today.
- Add/Remove Programs entry, Start Menu shortcut, uninstaller, `/SILENT` and `/VERYSILENT`.
- The `OpenWithList` registrations for the ~24 extensions `install.ps1` already writes, plus
  `FriendlyAppName`, `DefaultIcon`, `SupportedTypes`, and the PATH entry. **Read `install.ps1` and
  mirror it** — it is the tested list, and it also documents why the default `.txt` handler is
  deliberately not seized (Win10/11 tamper-check the UserChoice hash).
- License page showing `LICENSE.txt`.
- **Running-instance handling is the requirement this exists for.** Today's answer is "close Newtpad
  first, never `-Force`, because a hard kill skips the hot-exit session write and loses unsaved
  tabs." The installer must ask the running instance to close **gracefully** (`CloseMainWindow`-style
  — a `WM_CLOSE`, which runs hot exit) and only then replace the exe. **Never a hard kill.** If it
  will not close, abort the install and say why; a failed install is recoverable and lost tabs are
  not.

**Build integration:** a `-Installer` switch on `release.ps1` (or a small `build-installer.ps1`).
It must **detect `ISCC.exe`** at the two default install paths and, when absent, print how to get it
(`winget install JRSoftware.InnoSetup`) and **skip without failing**. `build.bat` stays a single Odin
invocation and is not touched.

**The signing step, stubbed:** one place in `release.ps1`, the exact `signtool.exe` invocation
present but commented, a clear no-op when no certificate is configured, and a comment saying it signs
**both** the exe and the setup.exe. **Never prompt for or store a password. Never commit a
certificate path.** Read `docs/development-loop.md` §Signing before writing a line of it.

**Portable stays first-class** (principle 5): the release keeps attaching the bare `newtpad.exe`; the
setup.exe is an additional asset.

**Verification is honest here or not at all.** `ISCC` is not installed, so the `.iss` cannot be
compiled on this machine. Do not claim it builds. State exactly what was verified (authored, read
against `install.ps1`'s registration list, script logic reviewed) and what was not (compiled, run,
uninstalled, upgraded over a running instance). Wyatt installs it on a real machine — that is the
test.

**Commits:** `Add an Inno Setup installer` · `Wire the installer into the release script` ·
`Stub the signing step`
