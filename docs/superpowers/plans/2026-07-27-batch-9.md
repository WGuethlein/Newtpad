## What the investigation settled, so no task re-derives it

Read before planning any task; both facts were checked against the code, not assumed.

### Shift is not part of a chord — and the code says so twice

`Binding` is `(key, ctrl, alt, ctx)` (`commands.odin:256`). `commands.odin:252-254`: *"shift is …
not part of the chord — no command distinguishes on shift."* `commands.odin:294` carries the scar:
*"Ctrl+Shift+S can't be expressed: shift isn't part of a chord."* §6y was already caught by this once,
when §6u's plan proposed `Ctrl+Shift+arrow` for column select.

**Consequences, both load-bearing:**

- **Bookmarks cannot bind `F2` and `Shift+F2` as two chords.** One command reads `ev.shift` and steps
  backwards, exactly as `doc_cursor_left(doc, ev.shift)` does (`commands.odin:857`).
- **`keys.txt` must reject a chord containing `shift`** with a clear warning, not silently drop the
  modifier and bind `Ctrl+X` when the user wrote `Ctrl+Shift+X`. Silently binding something the user
  did not ask for is worse than refusing.

### There are no F-keys in the tree

`plat.Key` (`window.odin:117-124`) is A–Z, Num0–9, arrows/Home/End/Page, Backspace/Delete/Enter/Tab/
Escape, Plus/Minus. **No F1–F12**, and `vk_to_key` has no cases for them, so `VK_F2` currently
resolves to `.None` and is swallowed. Task 2 must add them to the enum *and* the switch. Add the full
F1–F12 range in one go rather than F2 alone — a partial range is the kind of thing the next person
re-discovers.

## Task 1 — the `keys.txt` user keymap overlay

**Goal:** a user file overrides `default_bindings`, with the app never becoming unusable because of it.

**File:** `%APPDATA%\Newtpad\keys.txt`, resolved through the same `session_dir()` that honours
`NEWTPAD_SESSION_DIR` (so tests never touch the real store). Format, one per line:

```
# comment
ctrl+shift+k = Nothing      <- REJECTED with a warning: shift is not part of a chord
ctrl+k       = Duplicate_Line
alt+up       =              <- empty command unbinds the chord
```

Context: **scope the file to `.Editor` only** and say so in the seeded header. Exposing `ctx` as a
column invites binding into `.Palette`, which is a text field and where a wrong binding is least
recoverable. If a real need for other contexts appears, add a column later — widening a format is
easy, narrowing it is not.

**Resolution:** `lookup_binding` gains an overlay pass that runs **first**, then falls through to
`default_bindings`. Keep `resolve_key`'s existing fallback chain (`commands.odin:642-659`) untouched —
the Find/Menu ctrl-or-alt fallback and the History passthrough are §6f fixes and must keep working.

**Reserved chords — decide the set, do not discover it.** At minimum `Escape` in every context and
whatever closes the surface you are in; a file that can strand the user in a modal surface with no
exit is a data-loss path (unsaved buffer, no way to reach Save). Refuse to bind those, warn, and
carry on with the rest of the file. State the escape hatch — *delete `keys.txt`* — in the seeded
header comment, because someone who has bricked their keymap cannot read the docs from inside the app.

**Duplicates within the overlay: last wins**, stated in the header. Chosen, not emergent.

**`View ▸ Edit Keybindings...`** writes the file if absent — seeded with every default binding,
commented out, so the file doubles as documentation — then opens it as a tab. Mirror
*Edit Current Theme...* (§6x) including its reload-on-save behaviour.

**Tests — `keymaptest`, over a pure parse function on file bytes (no window):** a good file; unknown
command name ignored; malformed chord ignored; a `shift+` chord rejected; empty command unbinds; a
duplicate chord (last wins); an overlay entry beating a default; a reserved chord refused; a file
that is entirely garbage leaves `default_bindings` intact. Assert through `resolve_key`, not just the
parser, or the test proves parsing and not binding. Sabotage each.

**Commits:** `Load a user keymap overlay from keys.txt` + `Add a menu row to edit the keybindings`

## Task 2 — bookmarks

**Goal:** `Ctrl+F2` toggles, `F2` / `Shift+F2` cycle, gutter marks, persisted per tab.

1. **Add `F1`–`F12` to `plat.Key` and `vk_to_key`** (`window.odin`). Exhaustive-switch pressure will
   point at anything that must handle them.
2. **Commands:** `Bookmark_Toggle` (`Ctrl+F2`) and `Bookmark_Cycle` (`F2`) — **one** cycle command
   reading `ev.shift` for direction, per the investigation above. Both `.Editor`.
3. **Storage:** `bookmarks: [dynamic]int` on `Document`, **byte offsets of line starts**, kept sorted.
   Not line numbers: §6y measured that turning a line number into an offset here walks from byte 0
   (48 ms/frame at line 28,000 of a 500 KiB log) and re-anchored the whole column-edit model onto
   offsets for exactly this reason.
4. **Edits shift them.** This is the task's real work. `find_invalidate` and `apply_snapshot` already
   solve this shape for the match list and the column rectangle — **read both and follow, do not
   invent a third pattern.** Required behaviour: an insert or delete *before* a bookmark shifts it by
   the delta; a delete that *spans* a bookmarked line start drops that bookmark; undo/redo restores
   the set that belonged to the restored state.
5. **Gutter mark.** `GUTTER_W` is one value added by both `col_x` and `col_at_x` (§6h) so the drawn
   and hit-tested columns cannot disagree — do not add a second width. If no gutter is shown in plain
   text view today, draw the mark in the left margin and say so; do not turn the gutter on as a side
   effect (that is Wyatt's toggle, and it belongs to the batching work).
6. **Session format 4 → 5**, one appended field per tab, tolerant ladder (v1–v4 still load, per §6z).
   **A tab whose disk stamp changed while closed drops its bookmarks** rather than restoring offsets
   onto shifted text — same "trust disk for clean" reasoning as §6b, and the alternative is bookmarks
   silently pointing at the wrong lines.

**Tests — `bookmarktest`:** toggle on/off; next/prev with wrap; **insert above shifts the offset**;
**delete of the bookmarked line drops it**; undo restores; empty-set cycle is a no-op not a crash;
session v5 round-trip; a hand-written v4 session still loads (the shape §6z's `viewmemtest` fix used);
a changed disk stamp drops them. Sabotage each — particularly the shift, which is the one that will
be wrong.

**Commits:** `Add F-keys to the platform key set` · `Bookmark lines and cycle between them` ·
`Persist bookmarks in the session`

## Task 3 — scrollbar match marks

**Goal:** ticks on the vertical scrollbar showing where find matches are.

The bar is byte-proportional (§6b), so `y = track_top + (offset / pt.length) * track_h`. No line
index, which is why this is cheap.

**Bucket by pixel row — one quad per occupied row, not one per match.** A 200 MB log with 50,000
matches would otherwise be 50,000 quads on a bar a few hundred pixels tall, and `quads_draw` takes a
slice per call. Build the bucket set once per frame from the published match count.

**Respect the worker.** Matches stream in (§6e) and `MAX_MATCHES` saturates independently of the scan
cap. Render from what exists now; when `find.truncated` is set the marks are incomplete and the UI
must not imply otherwise — the counter already shows a trailing `+`, so match that.

**Colour:** a role from `theme.odin`, not a literal. There are `Syn_*` and find-related roles already;
add one if none fits rather than reusing a semantically wrong one.

**Tests — `matchmarkstest`:** N matches inside one pixel row collapse to one mark; a match at offset 0
lands at the track top and one at `pt.length` at the bottom; an empty match set draws nothing; a
truncated set is flagged. Sabotage the bucketing (emit one quad per match) and assert the count.

**Commit:** `Mark find matches on the scrollbar`

## Task 4 — filter click-to-jump

§6h item 2. `filter_lines[i]` is already the byte offset of the line start, so this is a hit-test plus
`set_cursor` plus leaving filter mode.

`doc_filter_max_top` and the filter draw already share their layout — ask that, do not re-derive the
row height. **A click in the gutter must select the row**, not map to a negative column: filter view
draws line numbers and `GUTTER_W` shifts `col_x`/`col_at_x` together.

Leaving filter mode must go through whatever `Find_Toggle_Filter` does, so one path clears
`filter_lines`, `filter_top` and the banner — not a second teardown that drifts from it.

**Tests:** extend `findtest` — a click on filter row *i* leaves the cursor at `filter_lines[i]` and
filter mode off; a click in the gutter selects the same row; a click past the last row is a no-op.
Sabotage by off-by-one on the row index, which is the failure this will actually have.

**Commit:** `Jump to the line you click in filter view`

## Task 5 — filter's first paint

§6e's outstanding gap and the last thing owed against *"no frame ever shows emptiness."*

**Add a bounded synchronous pass from offset 0** that fills enough `filter_lines` to paint one screen,
with the worker continuing behind it and merging as it does today.

**The bound is the design.** Budget in **bytes scanned**, not matches found — a sparse query finds
nothing and an unbounded "until the screen is full" scan is a multi-GB stall on the UI thread, which
re-opens the P0 roadmap item 1 closed. Stop at the budget whether or not the screen filled; a
partially-filled first frame is fine, a frozen one is not.

Pick the budget from a measurement, not a guess: `regextest` already reports per-keystroke latency and
`SEARCH_SYNC_MAX` (256 KB) is the existing precedent for "small enough to do inline" (§6e). Justify
the number chosen against a target frame budget and **write the measurement into the report**.

When the budget is exhausted with nothing found, the view must say it is still searching rather than
showing a bare empty grid — that is the actual requirement.

**Tests:** extend `findtest` with a fixture whose first match is deliberately past the budget: the
first frame shows an explicit searching state, never a bare empty grid; and a fixture whose first
match is early: the first frame has rows. Add a **falsifier** reporting the worst-case synchronous
scan time, the way `regextest` does — a bound nobody measured is the bug.

**Commit:** `Paint filter view on the first frame`
