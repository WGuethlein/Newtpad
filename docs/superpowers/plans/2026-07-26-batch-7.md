## What the investigation settled, so no task re-derives it

Two questions the spec deferred to the plan are now answered against the code.

### Every measurement already starts at a row start

`text_cells`, `text_bytes_for_cells` and `text_span_cells` each walk their slice from index 0 while
accumulating a running cell column — **they already know the column at every rune**, they simply
never pass it to the tab decision. And the consumers pass row-anchored slices:

| Site | Slice | Origin |
|---|---|---|
| `doc.odin:2671,2673` (draw) | `line_buf[:n]` from the row start, at `col_x(char_w, 0, rhs)` | 0 ✓ |
| `doc.odin:2681` (caret) | `line_buf[:cprefix]`, same buffer | 0 ✓ |
| `doc.odin:2102` `line_cell_col` | `pt_read` from `ls` | 0 ✓ |
| `doc.odin:2111` `line_offset_at_cell` | `pt_read` from `ls` | 0 ✓ |
| `table.odin`, `markdown.odin` | a field / a table cell | its own 0, correct by construction |
| `ui_tabs.odin:209`, `menu.odin:374` | a label | 0 ✓ |

So **no `col0` parameter is needed on the measuring procs.** The spec proposed one; the code makes
it unnecessary, and an unused parameter on four hot procs is worse than none. This is the plan
correcting the spec, which `docs/development-loop.md` §1 explicitly expects.

### Tab stops are computed from the start of the **visual row** — a documented deviation

`wrap_row_end` (`doc.odin:329`) begins each visual row at `col = 0` and has no access to the logical
line's column. Threading one through it, `next_visual_row`, `visible_begin` and every walk that
consumes them is a large change.

**Decision: tab stops are relative to the visual row start.**

- **Wrap off** — the normal case, the only case for `.tsv`, and the only case column editing permits
  (§6y) — a visual row *is* its logical line, so this is exactly correct.
- **Wrap on**, a tab on a *continuation* row aligns to that row rather than to the logical line.
  Bounded and rare: leading indentation lives on the first visual row, where the origin is right.

What matters more than the deviation is that **the draw and the hit-test use the same convention**,
which they do, because both measure from the row start. That is the Shape-B property; record it in
the code comment as the reason, not as an apology.

## Task 1 — make the tab column explicit (no behaviour change)

**Goal:** every site that decides a tab's width knows the column it is at. Behaviour bit-identical:
`TAB_CELLS` stays 4 and tabs stay a fixed 4 cells. This commit must be a pure refactor.

**Do not add a defaulted parameter.** Change `text_cell_width`'s signature so the column is
**required**, and let the compiler enumerate the call sites. A defaulted `col := 0` would compile
everywhere unchanged and silently leave the wrong behaviour at exactly the sites this task exists to
find. This is the same compiler-enforced discipline as `[Command_Id]Command` and the exhaustive
`switch`es (CLAUDE.md, §6j).

In `src/platform/text.odin`:

```odin
// Cells a rune occupies when it begins at cell column `col` of its row.
// `col` matters only for '\t': a tab advances to the next tab stop, so its
// width depends on where it starts. Every other rune ignores it.
text_cell_width_at :: proc(t: ^Text, r: rune, col: int, set := Font_Set.UI) -> int
```

Keep the cached classification path exactly as it is; only the `r == '\t'` branch consults `col`.
In task 1 that branch still returns `TAB_CELLS` — wire the column through, change nothing about
what it computes.

**Call sites the compiler will surface** (all must pass a real running column, never a literal 0
unless the slice provably starts at a row start):

- `text.odin:527` `text_cells` — pass its own accumulating `col`
- `text.odin:538` `text_bytes_for_cells` — pass its own accumulating `col`
- `text.odin:620` `text_draw_spans` — **add a running cell counter**; it currently tracks only
  `pen` (a pixel), and `pen` is not a column once a tab is variable-width
- `text.odin:760` `text_span_cells` — it accumulates `col` *before* `start` and `cells` after;
  the column to pass is `col + cells`, not either one alone. **This is the easiest site in the
  batch to get wrong.**
- `doc.odin:297` `line_wrap_decision` — has `cells`
- `doc.odin:349` `wrap_row_end` — has `col` (the visual-row origin, per the decision above)
- `block.odin:381` — read the loop and pass its running column

**Verify:** `odin test src\base -collection:src=src`, then `build.bat`, then `celltest`, `wraptest`,
`wraplongtest`, `hscrolltest`, `csvtest`, `tablecellstest`, `mdtest`, `blocktest`, `linktest`,
`vnavtest`. All must pass **unchanged** — that is the entire acceptance criterion for this task.
Set `NEWTPAD_SESSION_DIR` to a temp dir first. Never run `drawcount`.

**Commit:** `Thread the cell column through the tab-width decision`

## Task 2 — true tab stops

**Goal:** a tab advances to the next multiple of `tab_width` (default 4, configurable) measured from
the visual row start.

1. **Tab width lives on `Text`.** `text_cell_width_at` is in `platform` and cannot read program
   settings. Add `tab_width: int` to `Text` (init 4) plus `text_set_tab_width(t: ^Text, n: int)`,
   clamped to `[1, 16]` — a 0 would make the advance zero and hang the measuring loops, which is a
   freeze on the property Newtpad advertises. The clamp is not cosmetic; test it.
2. **The advance:** `n := t.tab_width; return n - (col % n)`. At column 0 with n=4 that is 4; at
   column 2 it is 2, landing on 4. Never 0, given the clamp.
3. **Delete `TAB_CELLS`** and the stale comment above it (`text.odin:491-492`, *"Tabs are one cell
   for now"*) — that comment is what put "tabs are one cell" into the 2026-07-25 audit.
4. **Settings row.** `settings.odin`: `tab_width: int`, default 4, persisted in the existing
   key/value format (unknown keys are ignored, so old builds interoperate). Follow the exact shape
   of a neighbouring integer row (`font_size`, `zoom_pct`) — including the parse, the write in the
   format string at `settings.odin:205`, and the row in the Settings tab. Call
   `text_set_tab_width` on load and on change; on change also invalidate whatever the font-change
   path invalidates, because every cached cell measurement is now wrong.

**Sabotage-verified test — `tabstoptest`, a new mode in `test_modes.odin`.** The required property
is that **the same rune measures differently at different columns**:

- `text_cell_width_at(t, '\t', 0)` == 4, `(…, 1)` == 3, `(…, 2)` == 2, `(…, 3)` == 1, `(…, 4)` == 4
- `text_cells(t, "a\tb")` — `a`=1, tab advances 3 to reach 4, `b`=1 → 6. Under the old fixed-4 this
  was 6 too, **so this assertion alone cannot fail** — include `"ab\tc"` (2 + 2 + 1 = 5, was 2+4+1=7)
  which can.
- tab_width 8: `"a\tb"` → 1 + 7 + 1 = 9
- clamp: `text_set_tab_width(t, 0)` leaves a width that never returns a 0 advance
- **round-trip agreement:** for a line containing tabs, `text_bytes_for_cells(text_cells(prefix))`
  returns the prefix length for every prefix — the drawn column and the hit-tested column agree.
  This is the seam test; a unit test of the advance alone would not catch a consumer that forgot to
  thread the column.

Then sabotage: restore the fixed `TAB_CELLS` behaviour in the tab branch, run `tabstoptest`, **record
the exact failure output in the report**, restore the fix. A test whose failure output is not in the
report is not evidence (`docs/development-loop.md` §3).

**Also re-run** every suite from task 1. `wraptest`/`wraplongtest` and `csvtest`/`tablecellstest` are
the ones most likely to move, and if one does, that is a finding to report, not a number to update.

**Commit:** `Advance tabs to the next tab stop` + `Add a tab-width setting`

## Task 3 — `\\?\` long paths

**Goal:** paths over ~260 characters open, save and stat. CLAUDE.md hard rule; zero occurrences in
the tree today.

**One helper in `src/platform`**, pure enough to test without a filesystem:

```odin
// UTF-8 -> wide, with the \\?\ prefix when the path is absolute and long
// enough to need it. Returns the plain wide form otherwise.
wide_path :: proc(path: string, allocator := context.temp_allocator) -> win.wstring
// The prefixing decision alone, as a testable string function.
long_path_form :: proc(path: string, allocator := context.temp_allocator) -> string
```

`long_path_form`'s rules, each of which is a test case:

| Input | Output | Why |
|---|---|---|
| relative (`sub\f.txt`) | unchanged | `\\?\` is invalid on a relative path |
| `C:\a\b.txt` (short) | unchanged | no need; keeps ordinary paths ordinary in a debugger |
| `C:\<260+ chars>` | `\\?\C:\…` | the point of the task |
| forward slashes | converted to `\` first | `\\?\` disables normalization |
| contains `..` or `.` | canonicalized **before** prefixing | ditto — and this ordering is the trap |
| `\\server\share\…` | `\\?\UNC\server\share\…` | UNC takes a different form |
| already `\\?\…` | unchanged | idempotent |

Apply `wide_path` at the **file-I/O** sites only: `file.odin:74, 119, 138, 196, 233, 234, 250, 565`
(`CreateFileW`, `GetFileAttributesExW`, `GetFileAttributesW`, `DeleteFileW`, and the rename pair).

**Deliberately excluded — and the diff must say so on each line**, because "missed" and "chose" are
indistinguishable later:

- `file.odin:510-511` `ShellExecuteW` (link open) — the shell rejects `\\?\`
- `file.odin:537-539, 555-557` the Explorer helpers — they hand the path to another process
- `file.odin:270` the comdlg filter and the Save dialog — comdlg32 does not accept it
- `window.odin`, `instance.odin` — a dropped path and the single-instance hand-off are both
  inter-process
- `text.odin:264` font files — always short, inside `%SystemRoot%`

**Tests:** a new `longpathtest` covering the table above as pure string assertions, plus **one real
round-trip**: create a directory nest under `%TEMP%` whose full path exceeds 260 characters, write a
file through the atomic-save path, stat it, read it back, delete it. Sabotage by disabling the
prefix and watching the round-trip fail with the real Win32 error.

**Commit:** `Open long paths through the \\?\ prefix`

## Task 4 — CSS and SQL line comments

**Goal:** `.css` stops treating `//` as a comment (it has none) and `.sql` recognises `--`.
Both disclosed as deliberate gaps in §6w.

`Keyword_Set` (`lex_c.odin:82`) is already data-not-branching. Add:

```odin
line_comment: string, // "//" for the C family, "--" for SQL, "" for CSS (none)
```

Set it on every existing table (the C family keeps `"//"`), then make the matcher consult the field
instead of testing `'/'` and `'/'` literally. `""` must mean *no line comment at all*, not "match
the empty string at every byte" — that inverted check would colour every file solid.

**Interactions to preserve, each a review risk:**

- The `regex` path (`lc_scan_regex`) keys off a leading `/` and exists because a regex containing
  `/*` was misread as a block-comment open (§6w). Changing the `//` test must not disturb it.
- CSS with `line_comment = ""` must still handle `/* */` normally — that is CSS's real comment form
  and the only one it has.
- SQL's `--` must not fire inside a string literal, and must not confuse the numeric path
  (`a - -1`).

**Shape A is the named risk.** §6w shipped this wrong twice (`lex_xml`, then
`lex_c_resync_valid`): *a stateful lexer must keep scanning for state past its token-buffer cap even
once it stops emitting.* Include a small-`out` case where the token buffer fills before a `/*` later
on the line, and assert `state_out` is still correct.

**Tests** in `src/base/lex_c_test.odin` (pure, no Document, no GPU):

- `.sql`: `-- SELECT x` → the whole run is one Comment token and `SELECT` is **not** a Keyword.
  This exact case is §6w's stated symptom; assert the specific word, per §6w's other lesson.
- `.css`: `a { background: url(https://x/y) }` → nothing after `//` is a comment; the declaration
  after it still lexes.
- `.css`: `/* c */` still comments, including unterminated-across-lines via `state_out`.
- `.c` regression: `//` still comments; a regex containing `/*` still does not open a comment.
- the small-`out` state case above.

Sabotage each by reverting `line_comment` to the hardcoded `//` and recording the failures.

**Commit:** `Give each C-family language its own line-comment marker`

## Task 5 — the findings batch 6 carried

Five independent fixes from HANDOFF §5. Each needs a test that can fail.

1. **Reopen size cap fails open.** It reads `doc.disk_stamp.size` — 0 on a failed stat, stale on a
   restored dirty tab. **Stat at the moment of the reopen** and use that; treat a failed stat as
   *over* the cap (refuse), not under. The guard exists to prevent a multi-second UI freeze, so its
   unknown case must be the safe one. Test: a stamp reporting 0 against a file that is actually
   large still refuses.
2. **`File ▸ Save` and `Edit ▸ Paste` are live on the Settings and Font pseudo-tabs.** Gate them
   row-by-row — `Tab_Close` shares `has_doc` and must stay live, so a single predicate is wrong.
3. **Paste rewrites a lone CR as a line break** via `convert_line_endings`. A lone CR inside a
   pasted CSV field or terminal output must survive. Fix the CR handling to convert only CRLF and
   leave a bare CR alone; test a paste containing `a\rb`.
4. **No test exercises any menu `checked` predicate.** Add semantic cases to `menutest`: toggle
   wrap and assert `is_wrapped` flips; same for `is_table` and one encoding predicate. Sabotage by
   inverting a predicate.
5. **`session_restore` has no comment** explaining why it deliberately never calls
   `app_apply_view_defaults`. The reasoning is in `app.odin`; state it at the site, referencing
   §6z's `viewmemtest` case so the next reader finds the test that holds the line.
