Decisions taken with Wyatt before planning, all three of which change the code:

2. **A file too large to index refuses the sort, and the summary row says why.** Not a background

## The thing that blocks everything: there is no absolute row index

`table.odin:454-461` states the constraint in its own words — zebra parity rides the *visible* row
index because *"a data row's absolute index is not knowable without counting newlines from byte 0,
which is unbounded on a multi-GB CSV"*. That comment is correct about today and it is the reason
three separate §10 rules are unbuilt:

- **Row numbers** (group B) are meaningless relative to the viewport. They need the absolute index.
- **Zebra parity** inverts on an odd-row scroll (HANDOFF §6aw, "Owed"). §6aw says parity *"should
  ride on whatever group B decides for the row-number gutter's absolute index"*.
- **The sort** (group C) has to enumerate rows at all.

`Line_Index` (`doc.odin:929`) already scans every byte of the original on a worker thread counting
newlines, but it publishes **only a total** — `line_count`, `indexed`, `done`, `fault`. No offsets.
So "which data row is at byte `doc.top`" cannot be answered from it.

**Task 1 fixes that once, for all three consumers.** It is also §14's owed *sparse index*, which
[requested-features.md](../../requested-features.md) lists as two-thirds built — so this is not new
scope invented for the table view, it is the missing third, and the table view is its first caller.

## Task 1 — sparse line-offset checkpoints

**File:** `src/program/doc.odin`.

Extend `Line_Index` so the worker that already walks every newline records a checkpoint every
`LINE_CKPT_STRIDE :: 4096` lines:

```odin
Line_Ckpt :: struct {
	offset:  int, // byte offset of the line's first byte
	line_no: int, // 0-based
}
```

Add to `Line_Index`: `ckpts: [dynamic]Line_Ckpt` plus `ckpt_n: int` (atomic — the count the UI side
is allowed to read; the worker appends then publishes, so a reader never sees a half-written entry).

Cost at the stride: a 100M-line file yields ~24k checkpoints at 16 bytes = **~390 KB**. State the
measured number for a real file in the report; do not assert this one from arithmetic alone.

**The lookup, which is the actual deliverable:**

```odin
// 0-based line number containing byte `at`. Bounded: binary-searches the
// published checkpoints, then counts newlines forward from the checkpoint at or
// before `at` -- at most LINE_CKPT_STRIDE lines of scanning, never a walk from
// byte 0.
doc_line_no_at :: proc(doc: ^Document, at: int) -> (line_no: int, exact: bool)
```

`exact = false` when the index has not reached `at` yet (`indexed < at`, or `ckpt_n == 0`). **Every
caller must handle `exact = false` by drawing nothing rather than drawing a wrong number** — this is
Shape A and the whole point of returning the flag. A reviewer should check each call site for it.

**Tests** (`doc.odin` selftest or a `test_modes.odin` mode — follow whichever the neighbouring index
code uses; if you add a mode make it **one-argument** and add it to the sweep list, per the
development loop's `keytest` incident):

- A fixture crossing at least two checkpoints. Assert `doc_line_no_at` at the first byte, the last
  byte, and both sides of a checkpoint boundary.
- **Sabotage, and record the output:** set `LINE_CKPT_STRIDE` to 1 and confirm the same answers, then
  break the binary search's boundary case (`<` for `<=`) and watch a boundary assertion fail. A test
  that only probes mid-stride offsets cannot see that bug.
- Assert `exact = false` before the worker finishes. If the fixture is small enough that the worker
  always wins the race, the assertion is vacuous — say so and construct one that isn't.

## Task 2 — the absolute row index, and zebra parity off it

**File:** `src/program/table.odin`.

One producer, next to the other "ONE producer" blocks:

```odin
// Absolute data-row index of visible row r. The header is line 0 and is not a
// data row, so data row 0 is line 1: this is doc_line_no_at(table_row_start) - 1.
table_abs_row :: proc(doc: ^Document, r: int) -> (n: int, ok: bool)
```

Then:

- **Zebra parity** becomes `table_abs_row(doc, r) % 2` instead of `r % 2`. When `ok = false` fall
  back to `r % 2` — banding is cosmetic, and a wrong band is not a wrong number. **Delete the
  comment at `table.odin:454-461` and replace it**; leaving a comment that says the absolute index is
  unknowable, next to code that uses it, is worse than no comment.
- **Test the parity, not the plumbing.** `tablegridtest` currently asserts nothing about the band's
  parity — §6aw found that changing colours, rule thickness and parity together left every suite
  green. Assert: scroll by one row, and the band under a *given absolute row* is the same colour it
  was before the scroll. Sabotage by reverting to `r % 2` and record the failure.

## Task 3 — group B: gutter, widths, alignment, resize

**File:** `src/program/table.odin`.

### 3a. The row-number gutter

56px, right-aligned, `Text_Dim` — **and here §10's `text_dim` stands, unlike the em dash.** §6aw
took `Text_Muted` for the dash because the dash carries information (empty vs missing). A row number
is redundant with the row's position, which the reader can already see; it is the exact case
`Text_Dim` is for. The current row gets `Text_Secondary` per §10. Record this reasoning in the
comment — the *dash* deviation is in HANDOFF §5, and a later reader needs to know why the gutter did
not follow it.

The gutter takes its 56px from x = 0, which `table_cols_layout`'s comment (`table.odin:213-215`)
already anticipates: *"§10's row-number gutter, group B, takes that 56px from the same origin."*

**This is a seam change.** `table_cols_layout` is the one producer of the x axis, consumed by the
draw, the cell hit-test, the link layout, the edit box and the h-scrollbar. Add the gutter width
**inside it**, as a `table_gutter_w()` the layout adds to its starting `x`. Do not offset the draw
and leave the hit-test at 0 — that is precisely the divergence the block comment says four of five
consumers used to have.

**Test the seam:** click at gutter_w − 1 and gutter_w + 1 and assert the first resolves to no cell
and the second to column 0's first byte. Sabotage by removing the gutter from the hit-test only, and
record the failure output.

Rows whose number is not `exact` yet draw **no number** (not a zero, not a guess).

### 3b. Column widths per §10

`table_compute_widths` already samples, but disagrees with §10 on three counts. Reconcile
deliberately and say which wins in the comment:

| | §10 | `table.odin` today |
|---|---|---|
| sample | 200 rows | `TABLE_SAMPLE :: 500` |
| clamp | 8–40 chars | `TABLE_COL_MIN :: 3`, `TABLE_COL_MAX :: 40` |
| leftover | distribute proportionally | not implemented |

Recommendation: **take §10's 8-char floor and the proportional distribution; keep 500 for the
sample.** A wider sample is strictly better information for the same bounded cost, and §10's "200" is
a budget, not a result. `TABLE_COL_MIN :: 3` is the one that actually shows — a 3-char column cannot
hold its own header — so that moves to 8. Flag the divergence from §10's literal number in the
comment so the next audit does not "fix" it back.

**Reuse batch 17's `md_table_fit_cells`** (the design doc: *"Two implementations of one rule is the
shape this project keeps getting bitten by"*), or state concretely why the surfaces differ. If they
genuinely do, say so in the HANDOFF entry, not only in a code comment.

### 3c. Numeric and date right-align

Detect from the same sample pass — a column is numeric when every non-empty sampled cell parses as a
number, date when every one matches a date shape. **Empty cells do not disqualify a column** (a
sparse numeric column is still numeric) but **a column with no non-empty cells at all is not
numeric** — that is a vacuous-all-true, and it is the same shape as the tests this project keeps
finding. Write the test for that case first.

Right-aligned cells draw at `col.x + col.w − TABLE_CELL_PAD_X − measured_width`. The **truncation
path must stay left-anchored** — cutting a right-aligned number from the left changes its value,
which is worse than an ellipsis.

### 3d. Drag to resize, double-click to fit

Header-edge hit zone ±4px. Dragging writes `doc.table_widths[c]`; double-click sets it to the
column's widest sampled cell, clamped to the same 8–40.

`table_compute_widths` runs *"when the view opens and after an edit"* (`table.odin:240-241`). A
user-resized column **must survive that recompute** or the width will snap back the next time a cell
is edited. Add a per-column "user set this" flag that the recompute honours. This is the one part of
3d with a non-obvious failure, so test it directly: resize, edit a cell, assert the width is
unchanged.

## Task 4 — group C: sort, malformed rows, summary row

**Files:** `src/program/table.odin`, plus a command in `commands.odin` if the palette should reach
the sort (check `command_in_palette` — and see the bug in Task 6, which is exactly a palette
dispatch that silently does nothing).

### 4a. Malformed-row marking

A row whose field count ≠ the header's gets a 2px `Warning` bar on its left edge and **stays in
place**. §10: *"Silently dropping data in a data viewer is the worst possible failure."* The draw
already distinguishes missing from empty (`col.c >= len(row.fields)`, `table.odin:478`) — this is the
mark for that case, so the two must agree by construction. Do this one **first**: it is independent,
it is visible, and the sort's tests want a malformed row in the fixture anyway.

Note the bar is drawn at x = 0, which is now the **gutter's** origin, not the first cell's. Decide
whether it sits left of the row number or between gutter and cells, and say why.

### 4b. The sort

**A permutation over row indices. The bytes never move.**

```odin
Table_Sort :: struct {
	col:  int,  // -1 = unsorted
	desc: bool,
	perm: [dynamic]int, // visible row -> absolute data-row index
}
```

Built by one bounded pass when a header is clicked, over at most `TABLE_SORT_MAX :: 1_000_000` data
rows. Above that the click is **refused** and the summary row says so (4c). Sort keys follow 3c's
column type: numeric columns compare numerically, everything else compares as bytes.

**The seam, and it is a data-loss seam.** With a sort active, `table_row_start(doc, r)` must resolve
through `perm` — a visible row is no longer the r-th line from `table_data_start`. Everything downstream
(`table_field_at`, `table_cell_at`, `table_edit_start`, the link layout, the draw's sequential walk)
reads through that one producer, so **change it there and nowhere else**. The draw's pass 1 currently
walks lines sequentially (`table.odin:431-444`) precisely because that walk *is*
`table_row_start`'s walk; under a sort that equivalence breaks and the draw must call the producer
per row.

`table_edit_line` (the byte anchor §6aw added) and `table_edit_anchored` are what keep an edit on its
own row across a reorder. §6aw laid that guard *"precisely for the task that builds the sort"* — this
is that task. Do not add a generation counter; §6aw rejected one because it depends on the sort's
author remembering to bump it, which is the exact miss the one-guard design closes.

**Tests, per the design doc's own instruction — test the seam, not the unit:**

- With a sort active, click a cell at the **first** and **last** visible row, with a **malformed row
  in the set**, and assert the resolved byte range is the one under the cursor.
- Assert an *edit* lands in the right line, by reading the bytes back. Not by comparing the resolved
  range to a computed one — that compares two derivations of the same expression.
- The case §6aw warns about: **equal-length lines**. A fixed-width CSV with zero-padded IDs, ISO
  dates and fixed status codes, sorted, edited. The offset-comparing guard passed this; the
  byte-comparing one must not.
- **Sabotage:** make `table_row_start` ignore `perm` and record the failure output.

### 4c. Summary row

Row count, column count, active sort — at the bottom of the grid. Also the honest place for the two
refusals this batch creates:

- `12,438,201 rows — too large to sort` past `TABLE_SORT_MAX`.
- Row count while `Line_Index` is still running is **approximate and must read as approximate**
  (`~4.2M rows`), not as a settled number that later changes.

## Task 5 — the exe's version resource

**Files:** `src/platform/newtpad.rc`, `build.bat`.

`newtpad.rc` embeds the manifest and the icon and nothing else, so the shipped exe has empty
`FileVersion`, `CompanyName`, `ProductName` and `FileDescription` (verified 2026-07-31 with
`Get-Item ... | Format-List VersionInfo` on the installed v0.33.0). Unsigned **and** metadata-less is
the shape of Defender's ML false positive that made a GitHub download fail with "Virus detected".

Add a `VERSIONINFO` block. **The version must come from `src/program/version.odin`'s
`NEWTPAD_VERSION`**, not be typed a second time — `release.ps1` already greps that file so the tag
and the binary cannot disagree, and a hand-typed `.rc` version would be a third place to forget.
Generate the `.rc`'s version lines in `build.bat` from it, or `#define` them; either is fine, but
**assert the built exe's `FileVersion` equals `NEWTPAD_VERSION`** rather than eyeballing it.

Independent of the other tasks — land it first, it is small and it unblocks nothing.
