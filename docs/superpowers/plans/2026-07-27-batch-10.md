## The precedence question, decided here so no task decides it at the keyboard

`highlight_merge_spans` (`highlight.odin:455`) takes `(lex_spans, link_spans)` and keeps lexer spans
that do **not** overlap a link — so the order today is **links > lexer**. Colour rules become a third
producer, and the order is:

> **links > lexer > rules.**

Rules are **lowest**. Reasoning, in the order it should be defended:

- **They never punch holes in real syntax colouring.** A rule matching `error` inside a JSON string
  or a C identifier would otherwise recolour part of a token, which makes correct code look broken —
  a worse failure than a rule not showing.
- **They win exactly where they are for.** The audience is arbitrary log and text files, which have
  either no lexer (`.txt`, `.log` beyond `lex_log`'s own patterns) or a sparse one. Where the lexer
  emits nothing, the rule is the only span and it shows.
- **Where a lexer *does* colour a keyword, it is already doing the job** the rule would duplicate.

This must be implemented by **extending `highlight_merge_spans` to N ordered producers**, not by
adding a second merge beside it. Its contract is strict — *sorted ascending by start, no overlaps* —
because `text_draw_spans` has **no defined behaviour** for overlapping input. A parallel path is how
that precondition gets violated, and the failure is undefined rendering, not a wrong colour.

## Task 1 — sort lines and remove duplicate lines

**Three commands:** `Sort_Lines`, `Sort_Lines_Desc`, `Remove_Duplicate_Lines`. Three rather than two
because shift is not part of a chord (§6ad), so a descending variant cannot be `Shift+`-anything.
Palette-only to start — no default chords. Adding a chord is a `keys.txt` line now, which is exactly
what §6ad shipped for.

**Scope:** the selected lines **expanded to whole lines at both ends**; the whole document when the
selection is empty. Expanding is not optional — a partial first or last line would be corrupted.

**Implementation shape, and it is the same for all three:**

1. Resolve the region to `[first_line_start, last_line_end)`.
2. **Refuse if the region exceeds the cap.** Use `SORT_MAX_BYTES :: 16 * 1024 * 1024` and
   `SORT_MAX_LINES :: 1_000_000`, whichever binds first. A refusal changes nothing and posts a note —
   the shape `BLOCK_EDIT_MAX_LINES` and the reopen cap already use. Do **not** truncate.
3. Read the region **once**, split, sort or dedupe in a temp buffer, write **once** through
   `pt_edit_replace`. Not a per-line edit loop: §5 measured 2,000 per-row splices at 64 ms with the
   tree fragmenting so every later read pays; one region replace costs what a single edit costs.
4. **One undo entry** via `doc_batch_begin`/`end`, as replace-all does (§6i). Getting this wrong
   means N Ctrl+Z, and with `UNDO_MAX :: 200` a large sort evicts the pre-sort state entirely — a
   data-loss path, not an annoyance.
5. **Drop bookmarks inside the region**, keep those outside. A sort reorders lines, so
   `bookmarks_shift_replace` cannot express where a bookmark went; leaving them is the §6ad Alt+Down
   bug again, and that one shipped. `Reload from Disk` and EOL conversion already drop, so this is the
   established answer, not a new one.

**Preserve, and each of these is a test:**

- **Line endings.** A CRLF document comes back CRLF. `detect_line_ending` counts only `\n` (§6ab), so
  the split must treat `\r\n` as one terminator and the join must re-emit the document's `eol`.
- **The trailing line.** Whether the document ends with a newline must not change. Every naive
  split/join either appends one or eats one.
- **Stability** for equal lines (ascending and descending both).
- **Case-insensitive compare**, per the decision — but a *stable* one, so `Foo` and `foo` keep their
  relative order rather than swapping arbitrarily.

**Dedupe:** keep the **first** occurrence, drop every later duplicate regardless of distance.
Comparison is exact bytes (not the sort's case-insensitive compare) — `Foo` and `foo` are different
lines. Say so in the palette description. Decide and assert whether a no-op dedupe pushes an undo
entry; **it should not** — an undo that does nothing is worse than none.

**Tests — `sortlinestest`:** ascending; descending; selection-scoped with partial lines at both ends;
whole-document; stability; CRLF preserved; no-trailing-newline preserved; one undo entry restores
everything; bookmarks inside the region dropped and outside kept; the cap refuses and changes nothing;
dedupe keeps the first occurrence across a distance; a no-op dedupe pushes no undo entry.

**Commits:** `Sort the selected lines` · `Remove duplicate lines`

## Task 2 — keyword→colour rules (`rules.txt`)

**File:** `%APPDATA%\Newtpad\rules.txt` via `session_dir()` (so tests never touch the real store).
One `pattern = Role_Name` per line, `#` comments, **literal substrings, not regex** — regex is
16–19 ms/MB (§6d) and this runs per visible row per frame. Say that in the seeded header, or someone
writes `^ERROR` and files a bug.

**Roles are `Color_Role` names**, so a rule cannot invent a colour and every rule is themeable for
free — the same `rules.txt` reads correctly in Dark and Light. Unknown roles, malformed lines and
duplicates: ignored with a logged warning, never fatal. Duplicates: last wins, stated in the header.

**`View ▸ Edit Colour Rules...`** seeds and opens the file, mirroring *Edit Keybindings...* (§6ad) and
*Edit Current Theme...* (§6x), including reload-on-save and the refused-line note.

**Precedence is decided above: links > lexer > rules.** Extend `highlight_merge_spans` to take
ordered producers and keep the highest-priority span wherever two overlap. Its existing two-producer
behaviour must be **unchanged** — `highlighttest`'s link-precedence cases are the regression guard and
must pass untouched.

**Bound the per-frame cost.** `RULES_MAX :: 64` patterns. A naive "for each rule, scan the row" is
O(rules × row) per row per frame, inside the budget the lexer already spends. Measure it: `drawcount`
is headless and reports draw calls plus an instance-stream digest (§6ab), so report the before/after
on a real file with rules active, and state the per-row cost at `RULES_MAX`. If it is over ~1 ms per
frame at the cap, lower the cap rather than shipping the number.

**Also respect the row token cap.** `HL_MAX_ROW_TOKENS` is 512 and the merge's `survivors` array is
sized by it (`highlight.odin:456`); rules add spans to the same budget. A row that saturates must
degrade visually, never overflow — and §5 already records that `Highlight_Row_Cache.cur_buf`
saturating is a *live* visual bug on dense wrapped lines, so do not make it worse.

**Tests — `rulestest`:** parse good / unknown-role / malformed / duplicate; a rule colours its match;
two overlapping rules resolve deterministically; **precedence asserted in both directions** against a
lexer token and against a link; an empty or absent file changes nothing (assert the span stream is
identical, not just that it does not crash); the row-token cap is respected. Plus the `drawcount`
before/after.

**Commit:** `Colour matching keywords from rules.txt`
