## 1. Fenced code blocks lose their state above the viewport

**Reported.** "The trailing backticks don't get recognized, they're even a different colour… it just
makes the rest of the file a codeblock. Also, when the code block start goes off screen, the viewport
stops rendering the whole codeblock."

**Root cause — confirmed. Both symptoms are one defect.** `markdown_draw`
([markdown.odin:723](../../../src/program/markdown.odin:723)) begins its scan at `top_byte` and
initialises `in_fence := false` unconditionally. Scroll so the opening fence is above the viewport and
the renderer believes it is outside a fence: the block's contents render as ordinary markdown, and the
*closing* fence then toggles `in_fence` **on** — so every line after the block becomes code. The
"trailing backticks aren't recognised" and "the block stops rendering" are the same lost bit, observed
after and before the closing fence respectively.

**Fix — reuse, not new machinery.** The plain editor already solved this. `doc_lex_state_at(doc, at,
window)` ([lex_index.odin:288](../../../src/program/lex_index.odin:288)) answers "what is the lexer's
state at this byte" via the background per-line index, falling back to a bounded resync on huge files.
`base.Lex_State` for the markdown lexer **already encodes "inside an unterminated fence"** — see
[lex_markdown.odin:37](../../../src/base/lex_markdown.odin:37). `markdown_draw` must seed `in_fence`
from `doc_lex_state_at(doc, top_byte, …)` instead of from `false`.

**The part the state bit cannot carry: the language tag.** `Lex_State` is a scalar; it says *that* we
are in a fence, not that the fence said `json`. Resolution, in order:

1. **Indexed path (small files, the common case).** The per-line index makes the fence-open line
   findable in O(log n): binary-search for the largest offset below `top_byte` whose recorded state
   transitions from not-in-fence to in-fence, read that one line, and hand it to `md_fence_lexer`.
   Exact, one extra line read.
2. **Resync path (huge files, or a stale index).** The tag may sit outside the resync window and is
   then genuinely unrecoverable at bounded cost. Degrade to an **uncoloured** code block: the
   background and the suppression of markdown parsing are still correct, only the syntax colours are
   absent. Document this at the call site.

**Explicitly not:** scanning backward a fixed number of bytes for a fence marker. A fence can be
arbitrarily far above the viewport, so a bounded backward scan returns a confident wrong answer — the
Shape A failure the [development loop §4](../../development-loop.md) records seven instances of.

**Test.** `mdfencetest` (new headless mode). A fixture with a `~~~json` block whose opening fence is
100 lines above the viewport; assert (a) the rows inside the block draw with the code background and
JSON token colours, (b) the row *after* the closing fence draws as body text, not code. **Sabotage:**
restore `in_fence := false` and confirm both assertions fail — the second is the one that proves the
"rest of the file becomes code" symptom is covered.

## 2. Vertical scrollbar thumb stops short of the track bottom

**Reported.** "The vertical scrollbar doesn't go to the bottom of the screen anymore, only about 80%
of the way."

**Root cause — confirmed.** [main.odin:1151](../../../src/program/main.odin:1151):

```odin
b.thumb_y = clamp(b.track_y + f32(doc.top) / total * travel, …)   // total = doc.pt.length
```

`doc.top` is the byte offset of the **top visible line**, which at the document end is
`doc_max_top(...)`, not `pt.length`. The ratio therefore peaks at
`(length − one screenful) / length` and the thumb falls short by exactly the visible fraction of the
file. On a document where a screen is a fifth of the content, it stops at 80% — which is the number
Wyatt measured by eye.

**Fix.** Map against the scrollable range: `doc.top / max(1, doc_max_top(...))`. **`vbar_drag_to`'s
inverse must change in the same commit** — the comment at
[main.odin:1141](../../../src/program/main.odin:1141) records that a mismatched forward/inverse pair
is what made "grab the thumb and hold still" drift by ~3%, and fixing one side alone reintroduces it
in the other direction.

**Test.** Extend the existing scrollbar mode: with `doc.top == doc_max_top(...)`, assert
`thumb_y + thumb_h == track_y + track_h` exactly; and assert round-trip identity
`vbar_drag_to(vscrollbar_geo(top).thumb_y) == top` across a sweep of `top` values including both ends.
**Sabotage:** revert the denominator to `pt.length`, confirm the end-of-document assertion fails and
the round-trip still passes (proving the two assertions catch different things).

## 3. Horizontal scrollbar only exists while the long line is visible

**Reported.** "The horizontal scrollbar only allows for expanding left/right if the large row is on
the screen; if it's not on the screen the horizontal scroll bar won't appear."

**Root cause — confirmed.** `doc_max_hscroll`
([doc.odin:3158](../../../src/program/doc.odin:3158)) walks `visible_begin`/`visible_next` — the
visible rows only. Scroll the long line off screen and the measured width collapses to whatever is on
screen now.

**Decision (Wyatt, this session): high-water mark.** Track the widest line measured so far, per
document; the range never shrinks during a session. Chosen over a background full-document scan
because it needs no new job, no invalidation, and breaks no rule — CLAUDE.md's viewport-first
constraint stays intact.

**Fix.** Add `max_cells_seen: int` to `Document`. `doc_max_hscroll` computes the visible widest as it
does today, raises `doc.max_cells_seen` to it, and returns the range derived from the stored value.
Reset it when the document's content is replaced (reload, Save As across a reformat) — **not** on an
ordinary edit, where a shrinking longest line simply leaves the range generous.

**Accepted limitation, to be stated in the HANDOFF entry rather than hidden:** on first open the range
is only as wide as what has been looked at, so it grows as you scroll. This is the cost of not
scanning, and it is the behaviour Wyatt chose knowing it.

**Test.** Fixture with one very long line at the top and short lines after. Measure `doc_max_hscroll`
with the long line visible, scroll past it, measure again: the second value must equal the first.
**Sabotage:** remove the high-water store and confirm the second measurement collapses.

## 4. New tabs appear in the middle of the rail

**Reported.** "Sometimes tabs get added in the middle of the tab list… it should always appear at the
end if it was newly created, dragged in, or opened."

**Root cause — confirmed.** `app_add` ([app.odin:139](../../../src/program/app.odin:139)) reuses the
first `nil` slot unless `at_end` is passed. Only `app_new_scratch`'s `+` path passes it; the
open-a-file path ([app.odin:219](../../../src/program/app.odin:219)), the second open path
([app.odin:265](../../../src/program/app.odin:265)) and session restore
([session.odin:433](../../../src/program/session.odin:433)) do not. Close a middle tab, open a file,
and it lands in the hole.

**Wyatt, on being shown the diagnosis: "I don't want random order tabs, unacceptable."** Treat tab
order as an invariant to be enforced and tested, not a placement heuristic to be improved.

**The invariant, stated once so the tests can check it directly:** *the rail's display order is the
order tabs were added, and the only thing that ever reorders it is an explicit user drag.* Nothing
else — not closing a tab, not opening one, not a session restore, not a Save As, not an external-change
reload — may move a tab relative to its neighbours.

**Fix.** **Remove the `at_end` parameter** rather than defaulting it: a parameter with one legal value
is a future caller's chance to get it wrong. `app_add` always appends after the last live tab.

**Session restore is the caller most likely to break the invariant, and it is not covered by the
`app_add` fix.** It replays a saved order, so appending in saved order is correct — but only if the
saved order *is* the display order and is replayed sequentially. If `session.odin` stores or replays by
slot index, restore will silently reorder Wyatt's tabs on every launch, which is the same defect
arriving by a different route. The implementer reads
[session.odin:433](../../../src/program/session.odin:433)'s restore loop **before** touching `app_add`,
and fixes the storage format here too if it records slots rather than order.

**Test — the invariant, not the symptom.** A single mode that drives a sequence of operations (open,
open, close middle, open, Save As, simulated external reload, save session, restore) and asserts the
display order after each step equals the expected order, with the drag as the only permitted mutation.
Checking one open-after-close case would pass while leaving three other routes to a scrambled rail.
**Sabotage:** restore the nil-slot reuse and confirm the assertion fails at the open-after-close step;
then separately make restore replay by slot index and confirm it fails at the restore step. Two
sabotages, because the invariant has two independent ways to break.

## 5. Every chrome glyph is split vertically

**Reported.** "The half-glyph issue still occurs on the tabs, haven't seen it on the other." Clarified:
*"all characters/glyphs in the tabs and menus are split vertically."* Document text is unaffected.

**Hypothesis — high confidence, must be verified before fixing.** Chrome text is drawn at
**fractional pixel positions**; document text is not. `text_draw_spans`
([text.odin:750](../../../src/platform/text.odin:750)) emits each glyph at
`{glyph_x + f32(g.left), y + f32(g.top)}` where `glyph_x` derives from the caller's `x`. Document text
comes off an integer grid (`text_char_width` rounds the advance to a whole pixel precisely so
"column n's left edge is exactly n*cell_w" — [text.odin:474](../../../src/platform/text.odin:474)).
Chrome text does not:

- `tab_base_y = ty + TAB_H*0.5 + UI_SMALL_PX*0.35` ([ui_tabs.odin:543](../../../src/program/ui_tabs.odin:543)) — fractional y at almost every font size.
- Tab x positions come from the shrink loop's `step := max(1, over / f32(count))`
  ([ui_tabs.odin:200](../../../src/program/ui_tabs.odin:200)) — fractional once any tab shrinks.
- `r.close_x + (TAB_CLOSE_W - char_w) * 0.5` ([ui_tabs.odin:574](../../../src/program/ui_tabs.odin:574)).

An integer-sized glyph quad at a fractional position is resampled across texel boundaries, which
produces exactly a vertical seam through every glyph.

**Verification step, before any fix.** Instrument `text_draw_spans` to log emitted `pos` values for one
chrome draw and one document draw. The hypothesis predicts fractional x/y for chrome and integral for
document. **If the values are integral in both, this hypothesis is wrong** and the cause is in the
atlas (UV rect off by a half-texel, or the sampler) — stop and re-diagnose rather than snapping
positions that were never the problem.

**Fix, if confirmed.** Round the final instance position to whole pixels inside `text_draw_spans` —
one place, fixing every chrome surface at once. This is a no-op for document text, which is already
integral, so it cannot regress the grid. Do **not** fix it by rounding each caller: there are dozens,
and the next one added would reintroduce it.

**Test.** Assert every emitted instance position is integral, for a chrome draw at a deliberately
fractional origin and at 150% DPI. **Sabotage:** remove the rounding and confirm the assertion fails.
This is the seam that matters — a screenshot cannot be asserted on, but the position can.

## 6. Markdown preview overlaps the status bar; the editor wastes a row

Two related findings under one reported symptom.

**Reported.** "When shrinking the view horizontally, occasionally there's a row of text that overlaps
the bottom cells" — clarified as **markdown preview and split preview**. And separately: *"the regular
viewbox can allow for another row of text or something… it has a good amount of whitespace at the
bottom of the viewport."*

**6a — preview overlap. Hypothesis, high confidence.** `markdown_draw` takes `ybot` from its caller and
loops `for y < ybot`. A row whose baseline is just above `ybot` still draws a full line height
*below* it. The editor path bounds itself through `doc_visible_rows`, which subtracts
`doc_bottom_bar_h`; the preview path passes its own `ybot`
([main.odin:1372](../../../src/program/main.odin:1372)) and must be checked for the same subtraction.
The implementer verifies which `ybot` each markdown caller passes before changing anything.

**Fix.** Bound the loop on the row's *bottom* edge, not its baseline: stop when
`y + line_h - px > ybot`. And ensure every markdown caller derives `ybot` from the same
`winh − doc_bottom_bar_h(doc)` the editor uses — one expression, per CLAUDE.md's one-layout rule.

**6b — the wasted row. Decision (Wyatt): draw a clipped partial row.** `doc_visible_rows`
([doc.odin:739](../../../src/program/doc.odin:739)) truncates with `int(…)`, discarding a partial row —
up to a full line height of dead space, plus the unmatched `TEXT_MARGIN_Y`.

**This is the riskiest item in the batch** and must be treated as such. `doc_visible_rows` feeds the
hit-test, the scroll clamp, selection, and the caret — the exact seam
[§6j](../../../HANDOFF.md) records sixteen bugs against. Approach:

- Keep `doc_visible_rows` as the count of **fully** visible rows for every consumer that reasons about
  reachability (scroll clamp, page keys).
- Add a separate `doc_drawn_rows` = visible + 1 when a partial row fits, used by the **draw only**,
  scissored to the content box so it cannot paint over the status bar.
- The hit-test must accept the partial row (clicking a half-visible line should place a caret in it),
  so it reads `doc_drawn_rows`, and `row_at_y` must clamp rather than run past the content box.

**Test — a seam test, not a unit test.** At a sweep of window heights including ones where the
remainder is 1px, `line_h − 1`, and exactly 0: assert the last drawn row's bottom never exceeds
`winh − doc_bottom_bar_h`, and assert that every row the draw produces is hit-testable back to its own
index. **Sabotage:** make the draw use `doc_visible_rows + 1` unconditionally and confirm the overlap
assertion fails at remainder 0.

## 7. No gap between a long tab label and its close button

**Root cause — confirmed.** [ui_tabs.odin:532](../../../src/program/ui_tabs.odin:532):

```odin
max_cells := int((r.w - TAB_CLOSE_W - sx(8)) / char_w)
```

The label is drawn from `x + TAB_PAD_L + TAB_DIRTY_W` — 12px in at 96 DPI — but the budget subtracts
only `sx(8)`. The elided label is allowed 4px more than the room between its start and `close_x`, and
no gap is reserved at all, so a long name runs into the `×`.

**Fix.** Budget from the same values the draw uses, plus an explicit gap:
`r.w − TAB_PAD_L − TAB_DIRTY_W − TAB_CLOSE_W − TAB_LABEL_GAP`, with `TAB_LABEL_GAP_96 :: 4`. Deriving
the budget from the draw's own constants rather than a hand-copied `sx(8)` is the actual fix; the gap
is the visible part.

**Test.** Seam test at boundary widths: assert the elided label's measured right edge is ≤
`close_x − TAB_LABEL_GAP`, for a name long enough to elide at `TAB_MIN_W`, at `TAB_MAX_W`, and at
150% DPI. **Sabotage:** restore `sx(8)` and confirm it fails.

## 8. The modified marker has no space before the name

**Reported.** "It's missing the space between the name and the asterisk like was in the design docs."
Confirmed by the screenshot: `*version.odin`.

**Root cause — confirmed.** `TAB_DIRTY_W_96 :: 8` ([ui_tabs.odin:23](../../../src/program/ui_tabs.odin:23))
reserves one glyph's width and no more, and the `*` is drawn at the slot's left edge
([ui_tabs.odin:566](../../../src/program/ui_tabs.odin:566)), so it butts against the label.

**Fix.** Widen the slot to `TAB_DIRTY_W_96 :: 12` — glyph plus a 4px gap — and leave the `*` at the
slot's left edge. Widening the slot preserves the property the slot exists for, which
[the batch 13 spec](2026-07-29-batch-13-shell-design.md) states as "reserve an 8px slot so the
truncation point never moves": the label's start is unchanged whether or not the file is dirty.
`tab_natural_w` picks the new width up automatically since it already sums `TAB_DIRTY_W`.

**Test.** Assert the label's x is identical for a modified and an unmodified document of the same
name, and that the gap between the `*`'s right edge and the label's left edge is ≥ 4px scaled.
**Sabotage:** set the slot back to 8 and confirm the gap assertion fails while the stability assertion
still passes — they must catch different things.

## 9. Link detection over-captures, and activation silently does nothing

**Reported.** "It highlights, but it captures a LOT more than it should. For example this gets caught:
`hello/world`… also the click to goto link/explorer doesn't work."

**Root cause — confirmed, and the two symptoms are connected.**
`looks_like_path` ([links.odin:184](../../../src/program/links.odin:184)) accepts **any** token
containing `/` or `\`:

```odin
has_sep := strings.contains(s, "\\") || strings.contains(s, "/")
return has_sep || link_is_text_ext(s)
```

So `hello/world`, `and/or`, `24/7`, `he/she` and every date written `07/28` become links. Separately,
`link_resolve` stats the target and returns `rok = false` on failure — and
[main.odin:689](../../../src/program/main.odin:689) then does **nothing at all**, with no message. The
over-captured tokens are precisely the ones that cannot resolve, so clicking an underlined
`hello/world` is a silent no-op. That is very likely what "the click doesn't work" is: the decoration
promises something detection invented and resolution declines.

**Decision (Wyatt): resolve-gate the decoration AND tighten the heuristic.**

**Fix, part 1 — tighten `looks_like_path`.** A bare separator is not evidence. Require one of:
a known text extension (`link_is_text_ext`, already exists); a path-ish prefix (`./`, `../`, `~/`, a
drive letter, or a UNC `\\`); or an absolute leading separator. `hello/world` satisfies none.

**Fix, part 2 — only decorate what will open.** `links_layout` gates the underline on the same
`link_resolve` the click runs, so anything underlined is guaranteed to activate. Cached per viewport,
not per frame: resolution is a `stat`, the viewport is bounded, and the cache is keyed on the token
string and invalidated on scroll or edit. **A stat on a network path can block** — the cache must
therefore be populated from the draw's existing bounded row walk and must never be consulted for rows
outside the viewport.

This also retires the §6l note about `ms-msdt:` rendering underlined while `link_resolve` would
decline it — with the gate in place, the decoration cannot outrun the resolver by construction.

**Fix, part 3 — never fail silently.** If a resolve fails at click time despite the gate (the file was
deleted between draw and click), show the existing error message rather than returning.

**Out of scope, deliberately:** §6l's open question 1 — a link spanning two wrapped visual rows is
still detected per visual row. Wyatt did not report it, it needs the logical-line detection §6l
describes, and folding it in here would put an unreported redesign inside a bug batch.

**Test.** Extend `linktest`: assert `hello/world`, `and/or`, `24/7`, `he/she` and `07/28/2026` produce
**no** link; assert `./notes.md`, `C:\temp\x.txt`, `..\a\b.txt` and `readme.md` still do. Then the
seam that matters: for a fixture directory, assert **every span that `links_layout` decorates resolves
successfully** — the invariant "underlined implies openable", checked directly rather than inferred.
**Sabotage:** restore the loose `has_sep` and confirm both the false-positive assertions and the
underlined-implies-openable invariant fail.

## 10. Task-list checkbox tick is not centred

**Reported.** "This works, though the X is at the bottom right of the box, not in the center in the
view."

**Root cause.** [markdown.odin:827](../../../src/program/markdown.odin:827) draws the box, then the
tick as a text glyph placed from the box's origin rather than from its centre — so the glyph's own
bearings push it down and right. A glyph's ink box is not its layout box.

**Fix.** Centre the tick on the box's centre using the measured glyph extent, the same way
`caption_btn` centres its geometry (`cx0 := x + (w - box) * 0.5`). Better still, draw the tick as
geometry rather than a glyph — `caption_btn`'s `.Close` case already draws a stepped X and the tick has
the same problem the caption buttons had: dependence on whatever the chrome font carries.

**Test.** Assert the tick's drawn centre equals the box's centre within a pixel, at 100% and 150% DPI.
**Sabotage:** restore origin-relative placement and confirm it fails.

## 11. A done task item mutes its base text but not its themed colours

**Reported.** "The base color text gets muted but the theme colors don't, maybe we just add a filter
over all colors dropping them the same percent as the white/base color?"

**Root cause — confirmed.** [markdown.odin:840](../../../src/program/markdown.odin:840) sets
`task_col = g_theme[.Text_Muted]` and passes it to `md_draw_inline` as the *base* colour. Every run
that carries its own role — code, links, emphasis, syntax spans inside a fence — resolves its own
colour and ignores the base entirely. So the prose mutes and nothing else does.

**Fix — Wyatt's proposal, which is the right one.** Apply a mute *transform* to every colour the
inline draw resolves, rather than substituting one base colour. Add:

```odin
md_mute :: proc(c: [4]f32, k: f32) -> [4]f32   // lerp c toward g_theme[.Bg_Base] by k
```

and have `md_draw_inline` apply it to each run's resolved colour when the item is done.

**The placeholder factor, derived rather than guessed.** Wyatt: "I don't know about the colour
shades… just put in a placeholder that would be close to the final anyway." Muting is a lerp toward
`Bg_Base`, so solve for the k that reproduces the theme's own muted tier from its primary tier —
`mute(Text_Primary) == Text_Muted`:

- Dark: k ≈ 0.28
- Light: k ≈ 0.24

**Ship `MD_DONE_MUTE :: 0.26`**, a single constant for both themes. It reproduces each theme's existing
`Text_Muted` from `Text_Primary` to within ~0.02 per channel, so it is consistent with the muted tier
Wyatt already accepts rather than being an arbitrary number. Name it as a tunable in the HANDOFF entry
so the live pass can move it.

**Test.** Assert a done item's link/code/emphasis runs are all strictly closer to `Bg_Base` than the
same runs in an undone item, and that `md_mute(Text_Primary, 0.26)` lands within 0.03 per channel of
`Text_Muted` in **both** themes. **Sabotage:** revert to substituting the base colour and confirm the
themed-run assertions fail while the prose one still passes.

## 14. Ctrl+H has no Replace All, and no affordance explaining how to replace

**Reported.** "Ctrl+H has no replace all button/keybind, also no explanation of what you're to do on
this menu… doesn't tell you how to replace."

**Fix — two parts, both required.**

1. **The action.** A `Replace All` command in the command table (so it appears in the palette by name),
   bound to `Ctrl+Alt+Enter`, plus a button in the replace row. `Enter` in the replace field replaces
   the current match and advances; that binding needs to exist too if it does not.
2. **The affordance.** The replace row currently shows fields and nothing else. Add the two actions as
   labelled buttons with their accelerators shown, the same way the menus render a shortcut column —
   which is what turns "I don't know what to do here" into a readable row.

The find bar is a layout with a hit-test, so **one `*_layout()` produces the button geometry, consumed
by the draw and the click** (CLAUDE.md's one-layout rule). This is the item most likely to reintroduce
a §6j seam bug, because it adds clickable geometry to a bar that just moved to the top of the window.

**Test.** Seam test: every button the draw emits is hit-testable back to its own command, at the
narrowest window width where the bar still renders. Plus a behaviour test — Replace All on a fixture
with overlapping candidates replaces every match exactly once and leaves the document's undo history
as a **single** entry. **Sabotage:** make Replace All loop from the caret rather than from the start,
and confirm the count assertion fails.
