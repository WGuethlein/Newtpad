Theme files

Your format needs nine more roles. Everything in this document is hard-coded to nothing — every colour on every screen resolves through one of these names, so a themer can restyle the whole app and a colour rule keeps working in both themes. New roles are marked NEW.

bg_hover — hover fill for any tab, menu item, settings row or palette row. If the hover colour is currently implicit, it needs a key: a themer cannot change what has no name.
accent_wash — the fill behind a selected settings row. Deriving it from accent by alpha breaks on a light custom theme.
focus_ring — defaults to accent, separable because a themer may want accent quiet and focus loud.
scrollbar_thumb — if the thumb colour is not already a role, make it one. It sits on bg_base and needs 3:1.
table_zebra — alternating row fill in table view, replacing the column rules (§10).
md_bold — the role list has md_italic but no bold. If that is still true, bold has nowhere to go.
md_code_bg — code spans and fenced blocks need a fill, not just a foreground (§9).
md_rule — thematic breaks, table borders, and the heading underline in preview.
md_list_mark — bullets and ordinals. Wants to be quieter than md_heading but louder than body.

1.3 Rules the palette obeys

One accent, state only. If a colour is not telling you something is selected, dirty, focused, found, or dangerous, it is a neutral. That single rule is what separates this from the accent-on-everything look.
Warm neutrals, chroma under 0.02. Every grey has a trace of the accent's hue in it. Cold greys read as tooling; warm greys read as paper. This is most of the "cosy".
Five syntax hues, no more. A sixth hue always looks arbitrary. Distinguish more token types by lightness within a hue instead — that is why syn_json_key is bright neutral rather than a new colour.
Type does hierarchy, colour does state. Heading level is size and weight, never hue — which is why all six markdown heading levels share md_heading.
Measure text on what it sits on. Selection, find matches, and the filter band all change the background under text; each of those pairs is listed with its own ratio above.
Store alphas, not resolved hex. Where a value is "12% accent", keep it as an alpha over the surface so it stays correct when a user replaces accent. The two files above resolve them only for readability.

DPI — the most likely source of "still looks a bit off"

This is a checklist to verify against the existing code, not an assumption that any of it is missing. A 1440p and a 1080p monitor side by side is the worst case, because dragging the window between them changes DPI mid-session and Windows hands back a suggested rect at the new scale. Where an item is already handled, the value it should be verified against is stated so it can be checked rather than rewritten.

  1. Per-monitor v2 awareness declared in the manifest (dpiAwareness = PerMonitorV2), not by calling SetProcessDpiAwareness at runtime. Manifest-declared awareness applies before the first window exists, so the first frame is already correct. v2 also gets you correctly scaled non-client area and dialogs.
  2. Confirm the WM_DPICHANGED order: take the suggested rect from lParam and SetWindowPos to it exactly, then rebuild the metrics struct, then re-bake the glyph atlas at the new pixel size, then invalidate. In that order — rebuilding the atlas before resizing wastes a bake.
  3. Round every metric once, at the point of scaling, into a struct. Compute m.tab_h = round(30 * s) once per DPI change and read m.tab_h everywhere. Never scale at the call site — that is how two things that should align end up one pixel apart at 125%.
  4. Hairlines: max(1, floor(s)), never round. At 125% a rounded hairline becomes 1px at an offset that straddles two device pixels and renders as two half-alpha lines — grey mush. Floor it and snap its position to an integer.
  5. Caption geometry is drawn, so scale the stroke too. The 10×10 box becomes round(10*s) and the 1px stroke becomes max(1, round(s)). At 150% that is a 15px box with a 2px stroke, which is right; a 1px stroke in a 15px box looks broken.
  6. Font size is the one thing to round to even. Cell width and line height derive from it, and an odd line height makes vertical centring inside a 30px row land on a half pixel. Round the pixel size to even, then derive.
  7. One atlas per (family, size, weight, DPI). Keep the previous DPI's atlas alive for a few seconds when dragging between monitors — users drag back and forth, and re-baking twice a second is the one place this design could actually stutter.
  8. Test matrix, whatever the current state: 100 / 125 / 150 / 175 / 200%, and the drag between the two real monitors. At each one, check the menu-bar hairline, the caption stroke, the status-bar cell dividers, and the active tab's left edge against the editor's left padding. Those four catch nearly everything.

Markdown — the priority

9.1 The grid is not the obstacle you think it is

You said the viewport is a fixed cell grid, so a real preview looks like a heavy lift. It is much lighter than it appears, because the preview pane does not need the grid at all. The grid exists to make caret arithmetic, column selection, and hit-testing O(1). The preview has no caret, no selection anchor, no column, and no editing — it is read-only output. So it can use free proportional layout while the editor pane keeps the grid untouched.

What the preview actually needs 1. a block list Block :: struct { kind, level, spans: []Span, indent } 2. a span list per block Span :: struct { text, style_flags, colour_role } 3. one text shaper given a font + a max width, emit positioned glyphs and a height -- this is the only new code 4. a scroll offset in pixels, not lines Because it is read-only, you never map a pixel back to a character except for one case: click-to-sync-scroll, which only needs the nearest BLOCK, not the nearest glyph. Store each block's y range and binary-search it -- eight lines of code instead of a reverse layout. The shaper, in full Proportional text needs per-glyph advances. That is one DirectWrite call (IDWriteFontFace->GetDesignGlyphMetrics) or one stbtt_GetCodepointHMetrics per glyph, cached in the same atlas map you already keep. Line breaking is greedy: accumulate advances, break at the last space before max width. Greedy is what browsers do for body text. No Knuth-Plass, no hyphenation. Cost Layout only the visible blocks plus a screen above and below. Cache each block's laid-out glyph positions, keyed by (block index, pane width). Invalidate a block on edit; invalidate all on resize or zoom. A 778-line document lays out ~40 visible blocks -- microseconds, once, per width.

That is the whole lift: a block/span parser you half have, a greedy shaper, and a per-block layout cache. No change to the editor's grid, no new pipeline — preview glyphs go into the same atlas and the same instanced draw call as everything else.

10 GB and still smooth

You said you do not care how, as long as it is seamless. "Seamless" has a precise UI meaning here: the caret never stops responding, no progress dialog ever appears, and partial results are visible while the rest is still being found. That is achievable, and the UI rules matter as much as the threading.

The one rule The UI thread never touches the file. It reads two things: a results buffer that a worker appends to, and an atomic progress counter. Both are read-only from the UI side, so there is no lock and no stall. Mechanism memory-map the file CreateFileMapping + MapViewOfFile in 256 MB views The OS pages in what you touch. A 10 GB file costs no RAM until read. line index, lazily a []i64 of line-start offsets, built by the worker 10 GB / ~80 bytes per line = ~134M lines = ~1 GB of index. Too much. Index every 1024th line instead: ~1 MB, and scan forward at most 1023 lines to find any line. Instant. filter on a worker chunk on 4 MB boundaries snapped to newlines, one job per hardware thread Odin: core:thread pool. Each job appends matches to its OWN buffer; the UI reads them in chunk order, so results stay sorted with no shared-state contention. results appear live the filter list grows as chunks land, top-down progress atomic bytes_scanned / total, read once per frame UI rules 1. no modal, ever the file opens instantly; the first screen of text is available before the index exists 2. progress is a hairline 2px accent bar along the BOTTOM of the filter band, width = fraction scanned. It disappears at 100%. This is the only "loading" affordance in the whole application. 3. count is provisional "1,284 lines so far…" while scanning, then "1,284 of 134,217,728 lines". Never a spinner. 4. Esc cancels sets an atomic flag; workers check it per chunk. Cancelling is instant and keeps the partial results. 5. scrollbar is honest thumb size reflects total bytes, not lines found 6. typing stays live the filter query debounces 120ms, then restarts the scan. Restarting a scan must be cheaper than a keystroke feels -- cancel, don't queue. 7. degrade one thing only at >2 GB, disable word wrap by default (wrap needs the full line index) and say so in the status bar: "Word wrap off -- large file". One honest sentence beats a silently different behaviour.

Zoom is your text-resize story. Ctrl+= scales the document; the chrome scales with the interface font setting. Together those cover 1.4.4 without a separate mechanism.
Gamma-correct text blending. Not an accessibility checkbox, but it is why the measured ratios are true. Blend light-on-dark text in linear space or every value in §1 is optimistic by roughly a weight.
