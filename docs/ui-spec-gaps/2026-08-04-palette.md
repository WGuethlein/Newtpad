# Command palette vs `ui-spec` §7 — the gap list

Companion to [2026-08-04-menus.md](2026-08-04-menus.md). Written because M2 there (two selection
colours) and the palette's selection bug are the same fix, so scoping the menu batch without reading
§7 would have meant doing that state split twice.

Method as before: `docs/ui-spec/newtpad-ui-spec-v1.md` §7 and §7.1 opened and read in full, checked
against `src/program/palette.odin` at v0.67.0.

**Score: 13 requirements — 6 built, 2 partial, 3 missing, 2 are decisions rather than gaps.**

The palette is in noticeably better shape than the menus. Its *ranking and row content* are done and
in places exceed the spec. What is wrong is **geometry** (three wrong numbers) and **one structural
absence** (no scroll) that is also the root of a HIGH defect the audit found independently.

## Wrong numbers — §7's geometry line

**Spec §7:** *"560 wide, top edge 88px below the window top, horizontally centred, max 12 rows then
scroll."*

| Value | Spec | Code (`palette_layout`, `palette.odin:245-268`) |
|---|---|---|
| Width | **560** | `min(sx(720), width - sx(80))` — **720** |
| Top edge | **88px** below window top | `l.y0 = sx(44)` — **44** |
| Max rows | 12, **then scroll** | 12, then **truncate** (see below) |

The width and top-edge numbers are a single-line fix each. Worth deciding deliberately rather than
just conforming, though — 720 was presumably chosen by eye against real content (the palette carries
a label *plus* a category column *plus* an accelerator column, and 560 is tight for that at the
default interface font). **If 720 is right, amend the spec; if 560 is right, change the code.** What
should not happen is the two staying in disagreement with nobody having decided.

## Missing

### PM1. There is no scroll — and this is the audit's HIGH defect

**Spec §7:** *"max 12 rows **then scroll**."*

**Code:** `l.nres = min(len(p.results), PALETTE_MAX_ROWS)` truncates the draw to 12. **There is no
scroll state in the file at all** — no `p.top`, no offset, nothing (`grep` for `p.top|scroll` in
`palette.odin` returns zero hits).

This is the same defect the audit reports independently as HIGH: *"palette keyboard selection walks
past the 12 drawn rows — nothing is highlighted and Enter runs an invisible result"*
([06-ui-shell.md](../audits/2026-08-04/06-ui-shell.md)). Two symptoms, one cause. Fixing the spec gap
fixes the bug; patching the bug without adding scroll would just clamp selection to 12 and make
results 13+ permanently unreachable.

**The menus already have the machinery** — `menu_visible_rows`, a dropdown scrollbar that takes the
wheel and drags, `MENU_MAX_ROWS`. The palette should borrow that rather than grow a second one.

### PM2. Bare text does not search commands

**Spec §7:** *"bare text searches commands **and** open tabs."*

**Code:** bare text searches **open tabs only**; commands need the `>` prefix. That is a deliberate
four-mode design (bare / `>` / `:` / `?`) documented in `features.md`, and it is coherent — but it is
not what §7 asks for, and it makes `>` mandatory for the palette's main job.

### PM3. No dimmed prefix hint row when empty

**Spec §7:** *"Show available prefixes as a dimmed hint row when empty."*

**Code:** prefixes are discoverable through the `?` mode, which is an explicit mode the user must
know to type — not an automatic hint on an empty query. The `?` list is good; it just is not this.

## Partial

### PP1. The entry point is a hamburger, not `>_`

**Spec §7.1** opens by rejecting the current shape: *"The magnifier-plus-rounded-fill shape reads as
'search your files', which is wrong."* It asks for a **`>_` glyph, 26×26, no fill until hover,
tooltip *Commands (Ctrl+P)*, collapsing at 460px**.

**Code:** the rail carries `☰` (`ui_tabs.odin:50`, *"hamburger menu button"*), which does open the
palette in command mode. So the entry point exists and lands in the right place — but a hamburger
reads as "menu", which is the same class of wrongness §7.1 is complaining about. The 460px collapse
breakpoint is separately unbuilt (`requested-features.md` §2, B2 — none of §5's breakpoints exist).

### PP2. No menu-bar `Commands` item

**Spec §7.1** asks for both entry points *"ideally"*: the rail glyph **and** a menu-bar item
*"Commands  Ctrl+P" after a divider, at the end of the menu bar*.

**Code:** `Palette_Open` is a row inside the View menu, not an item at the end of the menu bar. Cheap
to add; the bar is `File · Edit · View · Encoding · Help`.

## Two decisions, not gaps

These need Wyatt, because conforming would change shipped behaviour people may already rely on.

### PD1. `Ctrl+Tab` — cycle, or open the palette?

**Spec §7:** *"Ctrl+Tab opens it pre-filtered to tabs, most-recent-first."*

**Shipped:** `Ctrl+Tab` / `Shift+Ctrl+Tab` cycle tabs directly, **in strip order, not MRU**
(`features.md`, "Tabs and the session").

These are incompatible. The spec's version is the VS Code / browser model; the shipped version is the
simpler one and was built deliberately. Note the strip-order choice is *itself* load-bearing — Wyatt
has an explicit ruling that tab order must be stable (*"I don't want random order tabs,
unacceptable"*, HANDOFF §5 on `a.docs`), and MRU cycling is adjacent to that objection even though it
does not reorder the strip.

### PD2. May a command be palette-only?

**Spec §7:** *"**Every command in it is also in a menu.** The palette is a faster route, never the
only route."*

**Shipped:** six commands are palette-only with no menu row — Sort Lines, Sort Lines Descending,
Remove Duplicate Lines, Open Link Under Cursor, and Extend Column Selection Up/Down
(`features.md`, "Commands with no default chord"). The audit counts 72 palette-exposed against 59 in
menus.

Conforming means finding menu homes for the text operations (an Edit ▸ Text submenu is the obvious
one) — which is also the honest fix for their discoverability. Not conforming means amending §7.

*Related and already known:* **Extend Column Selection Left/Right are dead entries** — they appear in
the palette and do nothing when run from it, because they read the Shift state of the invoking key
event and the palette supplies none (`features.md`, "Known dead entries"). Whatever is decided here,
those two should not survive it in their current form.

## How this changes the menu batch

Only one item moves: **menus M2 (two selection colours) and the palette's selection handling should
be one task, not two.** The palette draws `Selection_List` for `i == p.selected` (`palette.odin:411`)
exactly as the menu draws it for `i == app.menu.item` — one colour, one state field, both conflating
"hovered" with "keyboard-selected". §6 asks for two colours in menus; §7 does not ask for it in the
palette, but the audit's *"`palette_hover` overwrites keyboard selection every frame, making arrow
keys inert"* is the same conflation and wants the same state split.

Everything else in the menu batch stands as ordered.
