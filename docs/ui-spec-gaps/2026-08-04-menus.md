# Menus vs `ui-spec` §6 — the gap list

> **STATUS 2026-08-04, after two finish batches (v0.68.0, v0.70.0). §6 IS DONE except motion.**
> M1, M2, M3, M4, P1, P2, P3 all shipped; **M5 was never a gap** (see the correction below); **M6
> (50ms opacity) is the only item deliberately left**, with the reduce-motion setting it depends on.
> §7's geometry conformed too — 560×88, and the 560 was *measured* rather than assumed.
> See "Still open" at the end.

Written 2026-08-04, after Wyatt's call that **the UI rework is a V1 gate and menus are the named
gap** (HANDOFF §6aa fork 1, reversed; `requested-features.md` §2).

Method: `docs/ui-spec/newtpad-ui-spec-v1.md` §6 was opened and read in full — all four numbered
problems and all eight "additional rules" — and each was checked against `src/program/menu.odin` at
v0.67.0. **Every line below cites the code that decides it.** CLAUDE.md forbids quoting a spec
section you have not opened; this file is what opening it produced.

**Score: 14 requirements — 5 built, 3 partial, 6 missing.**

The headline: the *content* rules are largely done (grouping, the dropped verb, disabled reasons,
per-dropdown width) and the *finish* rules are largely not (highlight inset, two selection colours,
motion, live values). That is the shape of "it's gotten better but it still doesn't match the spec" —
the menus behave correctly and look unfinished, which is exactly what §6 item 4's own framing
predicts.

## Partial — right idea, wrong number

### P1. The check gutter is unconditional, and is 28px not 26px

**Spec §6.1:** *"a fixed **26px** check gutter reserved on every row of a menu that contains any
checkable item, **and none on menus that do not**."*

**Code:** the label draws at `x0 + sx(28)` (`menu.odin:1279`) and the check at `x0 + sx(8)`
(`:1272`) — for **every** menu. The File and Help menus have no checkable item and still pay a 28px
indent, which the spec explicitly says they should not.

Two changes, both small: make the gutter conditional on `slice.any_of(items, it.checked != nil)`
(computed once where `dropdown_w` already walks the items), and make it 26.

### P2. The View menu's last group is five rows

**Spec §6.2:** *"Five groups, four dividers, **nothing longer than four rows**."*

**Code:** the View menu has 5 groups and 4 dividers — correct — but the customisation group is
`Theme_Edit, Keys_Edit, Rules_Edit, Open_Themes_Folder, Open_Logs_Folder` = **5 rows**.

Worth reading the comment sitting directly above that group: it says *"UI spec 6: five groups,
nothing longer than four rows -- this was one run of six mixing two different kinds of thing."* The
split was made correctly at four rows, and then **`Open_Themes_Folder` was added underneath the
comment citing the rule it broke.** A rule in prose does not defend itself; if the rework wants this
to hold, it wants an `#assert`-shaped check (`menutest` already asserts dropdown widths, so the
harness exists).

### P3. Panel width approximates the spec's budget in character cells

**Spec §6:** *"widest label + 26 check gutter + 24 gap + widest accelerator + 20 padding. Measure
once on open; never a fixed width."*

**Code:** `dropdown_w` (`menu.odin:1729-1747`) measures per dropdown on open — the "never a fixed
width" half is right, and it is per-dropdown rather than the old widest-row-anywhere. But the budget
is `len(title) + trailing + 8` **character cells**, not the specified pixel sum. The `+8` stands in
for 26 + 24 + 20 = 70px of gutter/gap/padding; at the default interface font that lands near enough
to look right, which is why nobody noticed, but it scales with the font's advance rather than with
DPI and it will drift the moment someone picks a wider interface font.

Low urgency, but it is one line and it makes P1's 26px real rather than notional.

## Missing

### M1. The highlight touches the panel edge — the spec's own headline

**Spec §6:** *"**Highlight inset:** 5px panel padding means the highlight never touches the panel
edge — **the single biggest reason the menus read as unfinished in the screenshots**."*

**Code:** `menu.odin:1268` draws the row highlight at `pos = {x0, y}, size = {dw, MENU_ITEM_H}` —
the full panel width, flush to both edges.

The product already knows how to do this: the filter dropdown's search row two lines earlier
(`:1251`) insets itself with `x0 + sx(4)` / `dw - sx(8)`. The row highlight just never got it.

**This is the single highest-value item in the file** — it is the spec's own nomination, it is one
expression, and it changes how every menu in the product reads.

### M2. One selection colour where the spec asks for two

**Spec §6:** *"**Two selection colours:** mouse hover uses `bg_hover`; keyboard cursor uses the
accent fill with `bg_base` text. Two states, two weights."*

**Code:** `menu.odin:1268` uses `g_theme[.Selection_List]` for `i == app.menu.item`, whichever way
the highlight got there, and the label colour never changes with it (`:1279`).

This needs `app.menu` to distinguish "hovered" from "keyboard-selected", which it currently collapses
into one `item` field — so it is a small state change, not just a colour swap. Note the audit's
finding that `palette_hover` overwrites keyboard selection every frame is **the same disease in the
palette** ([06-ui-shell.md](../audits/2026-08-04/06-ui-shell.md)); fixing both against one rule is
cheaper than fixing them twice.

### M3. Live values in labels

**Spec §6:** *"**Live values in labels:** *Reset Zoom (125%)*, *Tab Width (4)* — state without
opening Settings."*

**Code:** `menu_item_label` exists and is the right hook — but it returns `""` for everything except
`Table_Filter_Toggle` (`menu.odin`, first line of the proc). Zoom and Tab width show static titles.

The plumbing is already there and already used by the draw *and* the width budget through one lookup,
so this is filling in a proc, not adding a mechanism.

### M4. No 2px gap below the menu bar

**Spec §6:** *"2px gap below the bar."*

**Code:** `menu_origin` returns `TAB_STRIP_H + MENU_BAR_H` — flush.

### M5. ~~No horizontal flip~~ — WRONG, this was never a gap

**Corrected 2026-08-04 while implementing.** `menu_dropdown_rect` ends with
`x0 = min(ox, max(0, width - w))`, which clamps the panel inside the window. I read the file looking
for a *flip* and missed the *clamp* that achieves the same visible result. A dropdown that would
overrun the right edge slides left instead of overflowing, which is what §6's rule is for.

Left in place rather than deleted, because the failure is instructive: the gap list was built by
searching for the spec's vocabulary, and a correct implementation using different vocabulary read as
absent. **Grep for the behaviour, not the word.** The original text follows.

### M5 (original, incorrect). No horizontal flip, and context menus are where it bites

**Spec §6:** *"Flip left if it would leave the work area."*

**Code:** vertical flip-up exists and is carefully done (`menu_dropdown_rect` returns `y0` for
exactly this reason). There is **no horizontal clamp anywhere**. For a bar menu that is nearly
unreachable — the titles are at the left. For a **context menu it is ordinary**: `menu_origin`
returns `app.menu.ctx_x` raw, so a right-click on a table header near the right edge, or the column
filter dropdown on a right-hand column, draws a panel that runs off the window.

### M6. Nothing animates

**Spec §6:** *"**Motion:** opacity only, 50ms. No slide, no scale. Highlight movement is instant for
both mouse and keyboard."*

**Code:** nothing in the product animates (the 2026-08-04 audit confirmed this tree-wide; the only
timer is the caret blink). Note the second half is already satisfied by accident — highlight movement
*is* instant. What is missing is the 50ms opacity fade on open.

This is the one item here that is a genuine feature rather than a fix, and it is coupled to §18's
motion budget and the **"reduce motion" setting** (`requested-features.md` §2, ui-spec §11) which is
also unbuilt. Do them together or not at all — an animation with no way to turn it off is a
regression for the accessibility position, which is currently *"ships with no screen-reader
support"* and does not need a second strike.

## Suggested order

1. **M1** (highlight inset) — one expression, the spec's own headline, changes every menu.
2. **P1** (conditional 26px gutter) + **P3** (real pixel budget) — same code path, do together.
3. **M2** (two selection colours) — needs a state split; do it with the palette's identical bug.
4. **M5** (horizontal clamp) — a real defect on context menus, not just finish.
5. **M3** (live values) — fill in a proc that already exists.
6. **P2** (four-row cap) — plus a `menutest` assertion so it cannot regress a third time.
7. **M4** (2px gap) — trivial, fold into any of the above.
8. **M6** (motion) — last, and only with the reduce-motion setting.

**Not in this list, deliberately: the two menu defects the audit found** — context menus swapping
themselves for the File menu on arrow keys, and `menu_draw_dropdown` resolving scroll inside the draw
(HANDOFF §5). Both are in [06-ui-shell.md](../audits/2026-08-04/06-ui-shell.md), and both belong
*inside* the rework rather than before it: the scroll-in-draw violation has already been patched
three consecutive releases running (§6br → §6bt → §6bu), and a fourth patch to the same shape is the
thing the one-layout rule exists to stop.

## Landed in v0.70.0 — the rest of §6

- **M2 in the menu.** The concern that made it a second batch turned out not to hold: `menu_hit_test`
  resolves a click through `menu_item_at` **directly** and reads neither field, so only the keyboard
  cursor and the draw ever depended on `item`. The accent fill also cannot surprise a mouse user,
  because **only the keyboard-open path arms `item` at all** — a menu opened by clicking has
  `item == -1` until an arrow key moves it.
- **M3 in full.** `Reset Zoom (125%)`, `Font (tab width 4)`.
- **P2, with the assertion.** `menutest` now fails if any run between dividers exceeds four rows, and
  it **caught the live violation on its first run** (`View's longest run between dividers is 5 rows`).
  The fix cuts by kind — three rows that edit a config file, two that open a folder — which makes View
  six groups where §6.2 says five. Taken deliberately: §6.2's numbered complaint was *"eighteen items,
  **three** dividers, one rhythm"*, so the durable rules are group-by-kind and the cap; five was a
  description of the item set it was written against, and the menu has gained rows since.
- **§7's 560px width, measured rather than assumed.** `palettetest` now computes the widest Commands
  row from the command table and asserts the box fits it: **514 needed, 560 given, 46px of headroom.**
  It only became reachable because the three sentence-length titles came down — at 53 characters the
  floor was near 700, which is where the old 720 came from. If a future title eats the headroom the
  assertion fails instead of the row clipping silently.

## Still open

| Item | Why |
|---|---|
| **M6** (50ms opacity fade) | The only §6 item deliberately left, and it stays coupled to the **reduce-motion** setting (§11, unbuilt). An animation with no way to disable it is a regression against a position that is already "ships with no screen-reader support". Do them together or neither. |
| **§7's PM1** (palette scroll) | Not part of §6. `PALETTE_MAX_ROWS` truncates rather than scrolls, and that is also the audit's HIGH "selection walks past the drawn rows". See [the palette gap list](2026-08-04-palette.md). |
| **§7's PM2, PM3, PP1, PP2, PD1, PD2** | Bare-text search scope, the dimmed prefix hint, the `>_` entry glyph, the menu-bar Commands item, and the two decisions (Ctrl+Tab, palette-only commands). Same file. |

## What this file does not cover

§6 only. The other menu-adjacent sections — §7 (command palette), §11 (settings screens), §5
(narrow-window drop order), §18 (motion and focus) — have their own obligations and their own gaps,
and §5's breakpoints are known-absent (`requested-features.md` §2, B2). If the rework is scoped as
"menus" it should still read §7 before starting, because M2's fix and the palette's selection bug are
the same fix.
